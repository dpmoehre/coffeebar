# ✅ 已完成：产品定位与运行环境

## 这是什么

公司里的个人手冲 / 调酒吧台。用途是**把豆子和酒都管清楚**：冲的时候能查、能记、能看动画；酒也能查酒瓶、配方、酒单；还能看谁喝了、什么时候喝的、该补货了、一杯多少钱，并能出表。

产品范围（豆子 + 酒，同一套应用）：

- 豆卡：产地、风味、克重、照片、价格、每杯成本、维度打分
- 消耗流水：克重、**谁喝的标签**、消耗速度曲线、补货清单
- 冲煮指导：分步文字 + SVG 动画
- 酒：基酒（酒名、买入价、风味类型、酒精度）、酒瓶库存、推荐酒单、鸡尾酒、自制基酒配方
- 统计：顶部先出数字（消耗了多少豆、多少酒、花了多少钱），再画曲线、按人拆开；日历（咖啡+酒）；导出表格
- 部署：Windows 小主机上尽量「装一次、双击开」

## 明确不是

- 不是给同事点单、排队、支付的系统
- 不是后厨 KDS
- 不是多门店 / 公司 SSO

## 谁在哪用

**功能全端一致**：小主机、手机、其他电脑、cpolar 远端都能用豆子与酒的完整功能（档案、消耗、照片、冲煮动画、酒单配方、日历出表）。差别只在**页面布局**（桌面宽屏分栏 / 平板 / 手机单列），不按设备砍功能。

| 场景 | 设备 | 布局（功能相同） |
| ---- | ---- | ---- |
| 日常吧台 | 小主机自带屏幕 + 键鼠 | 桌面宽屏：豆库网格 + 豆卡侧栏或双栏 |
| 手里拍照、站着冲 | iPhone / iPad | 单列大按钮；相机入口更靠前，冲煮动画占满屏 |
| 换一台电脑 | 内网 Mac / Windows | 同桌面布局，随窗口宽度收成单列 |
| 外出临时 | cpolar | 与对应设备布局相同 |

拍照仍以手机最方便，但电脑也能选文件上传。冲煮动画在吧台大屏和手机上都能完整播放。

**不能有多端竞争**：功能可以都有，但**同一时刻不能两台设备同时改同一条数据**。细则见「无多端竞争」。

# ✅ 已完成：软件架构方案

## 形态

一套响应式网页，一台小主机跑完。不写四套原生 App。

```
[小主机 / 手机 / 其他电脑 / cpolar]
  同一套功能：豆子 · 酒 · 统计日历 · 出表
  只换布局，不换权限
        │
        ▼
   Caddy :80 ── FastAPI ── SQLite + photos
                 │
                 └── 写锁：同一条资源（豆/酒瓶/配方）同时一个写会话
                     网页之间可提示接管；MCP 写入硬拒绝
```

小主机上只保留三件事：

1. **反向代理**：Caddy（本机 80，转给应用端口）
2. **应用进程**：FastAPI 提供 API，并托管前端构建产物（或 Vite 开发时拆开）
3. **数据**：SQLite 单文件 + 本地图片目录

不引入微服务、消息队列、云 OSS、独立用户中心。

## 无多端竞争（硬约束）

多端**功能完整、布局不同**。禁止的是「两台设备同时改、互相覆盖」，不是「手机只能看」。

不做实时协同、不做 OT/CRDT、不做 last-write-wins 互踩。

服务端按**资源写锁**强制（按豆卡 / 酒瓶 / 配方，而不是按设备类型）：

- 任一端开始改某条资源或记一笔消耗时，持有该资源的短时写锁。
- 其他端仍可**完整浏览、播放冲煮动画、看日历**；同一条的并发写不合并。
- 本机多标签同样适用：同一条资源同时只接受一个写会话。
- SQLite 单文件单写者与此一致；不做多端会话协商以外的同步协议。

### 网页侧是软锁：提示接管，不是硬拒绝

这是**单人自用**系统，最高频的冲突不是两个人抢同一张豆卡，而是**自己在小主机开着编辑页，走到吧台又用手机改**。如果硬拒绝，人就被自己锁死，还得干等超时——这是纯负担，必须避免。

所以网页对网页用**软锁**：

- 第二处想写时，不直接拒，提示「另一处正在编辑这张豆卡（小主机 · 3 分钟前），要接管吗？」，点一下即接管。
- 接管后旧会话的锁失效。旧会话再点保存时明确报「已被其他窗口接管，你的这次修改没有保存」，并把它填的内容留在页面上可复制，不静默丢弃。
- 不做合并、不做 last-write-wins 静默覆盖：始终只有一个持锁者，冲突交给人一次点击决定。

锁的语义写死，别留模糊：

| 项 | 约定 |
| -- | -- |
| 存哪 | 存表（不是进程内存），服务重启后按时间戳自然过期，不留死锁 |
| 超时 | 无心跳 5 分钟自动过期 |
| 续锁 | 编辑页每 60 秒心跳续一次；页面隐藏或关闭即停止续锁 |
| 主动释放 | 保存成功、取消编辑、`beforeunload` 尽力上报 |
| 不占锁 | 播放冲煮动画、看统计、看画像、看日历、导出 CSV |

**MCP 写入仍是硬拒绝**：Agent 不该替人抢锁。网页正在编辑该资源时，MCP 返回明确错误（谁在编辑、多久前），由人决定是去网页保存还是让 Agent 重试，工具不自动接管、不自动轮询重试。

## 技术栈（已选定）

与仓库约定一致：Python 用 **uv**，前端用 **npm**，密钥与运行数据不入库。

- **前端**：Vite + React + Tailwind（设计 token）+ [anime.js](https://animejs.com/documentation/svg)（页面动效与冲煮 SVG）。**一套组件、响应式布局**：桌面宽屏 / 平板 / 手机只改栅格与触控尺寸，不拆第二套功能。
- **后端**：FastAPI（`uv`）。豆子/酒 CRUD、图片、流水、写锁、统计与 CSV 出表。
- **MCP**：本机 MCP Server，给 Cursor 调用，与网页共用 FastAPI / SQLite / 写锁。见下节。
- **数据库**：SQLite（例如小主机上的 `data/coffeebar.db`）。备份 = 拷文件。
- **图片**：`data/photos/`，不进 Git。iPhone 常见 HEIC，服务端转 JPEG/WebP 并生成缩略图。
- **入口**：内网 `http://小主机名或局域网IP`；本机也可 `http://localhost`。
- **进程与安装**：见「部署要简单」。Windows 开机可自启，日常应能双击启动，不要靠每次敲命令。
- **口令**：环境变量注入的简单口令，防止同事误改库存。cpolar 打开时必须有口令，且 token / 口令不入库。

备选（未采用）：Next.js 全栈。功能等价，但和「Python 用 uv」分叉，除非后续明确改口。

## 信息结构

```
Tag                       # 自由标签，输入即创建；可标在豆/酒/配方上
Person                    # 谁喝的：实体表（不是裸字符串）
Bean *──* Tag
Bottle *──* Tag
Recipe *──* Tag
Bean 1──* BeanPhoto       # kind=pack 包装 / tray 豆盘；都可缺
Bean 1──* BeanLot         # 同豆多袋：只加批次，不新建豆卡；用完仍留历史
Bean 1──* BeanScore       # 维度打分
Bean 1──* BrewGuide       # 只存参数（方式键 + dose + 比例），各段渲染时算
Bottle 1──* BottleLot     # 基酒/酒瓶批次：酒名在 Bottle，买入价与容量在批次
Recipe                    # 鸡尾酒或基酒/自制基酒
Recipe *──* Bottle        # 配方用到的酒/辅料
MenuItem                  # 推荐酒单条目 → Recipe 或 Bottle

# 两类事件，分工不同：

StockEvent                # 只改数的管理动作，没有「谁喝的」、不算钱
  kind = intake           #   入库（新袋/新瓶）
       | measure          #   开袋实称
       | adjust           #   中途盘点校正（可正可负）
       | close_lot        #   关袋/关瓶结清偏差
  → BeanLot | BottleLot

ConsumptionEvent          # 喝掉一次：咖啡和酒同一张表，避免双记
  kind = coffee | drink
  → BeanLot | BottleLot   # 扣哪一批次；钱按这一批次算
  → Person                # 谁喝的，可空
  amount_g | amount_ml
  unit_cost               # 当时单价快照，历史金额不回溯改写
  brew_*                  # 咖啡才有：方式键、粉量、比例、各段实际秒数、总时间
```

**库存真相 = `可用克重 − Σ消耗 − Σ校正`**，两张事件表一起算，不另存汇总数。

**统计、日历、画像只读 `ConsumptionEvent` 一张表**：咖啡冲一次就记这一条（它同时扣库存），不再另记一条饮用事件，所以"豆克数"和"咖啡杯数"永远来自同一批行，不会对不上。

# ✅ 已完成：全端布局、统一 UI、冲煮动画

## 功能 vs 布局

- **功能**：所有屏幕同一套路由与接口（豆库、豆卡、照片、消耗、冲煮播放/编辑）。
- **布局**：用断点换排版。小主机宽屏双栏、手机单列全宽动画、平板介于两者。
- **动效**：同一套 anime.js 时间轴；用 `createScope` + media query 只调整位移/尺寸，不维护两套动画逻辑。文档：[Anime.js Scope / 响应式动画](https://animejs.com/documentation/svg)（站点内 Scope 与 SVG 同属 v4 工具箱）。

## UI 风格（全站统一）

现代吧台，而不是后台表格风。全站共用一套 token（色、字、圆角、阴影、动效时长），禁止单页另起一套皮肤。

方向（落地时写成 CSS 变量，可微调，不另开主题系统）：

- 深色底（espresso）+ 奶油字 + 琥珀色点缀；卡片轻玻璃/软阴影。
- 大字号、少边框、豆卡照片做主视觉。
- 列表进入用 stagger；按钮/卡片有短反馈，不堆无意义循环闪烁。
- 字体与间距全站同一套；冲煮播放页也走同一色板，不做成「突然另一个 App」。

参考（只借交互与气质，不抄页面、不入库他人资源）：

- [Anime.js SVG](https://animejs.com/documentation/svg)：`createDrawable` 描线、`createMotionPath` 沿路径、`morphTo` 形变；官网示例把壶/车沿赛道走、把 path `draw` 从 `0 0` 画到 `0 1`。
- [Toololis Pour-Over Timer](https://toololis.com/pour-over-coffee-timer/)：V60 水位涨落 + 滴滤虚线 + 四段（闷蒸 / 一注 / 二注 / 滴滤）进度点。
- [Angus Pour Over Timer](https://anguszhu.com/pour-over-timer/)：全屏阶段进度、一眼能看「现在该注到多少克」。
- [stromland/coffee](https://github.com/stromland/coffee)：深色咖啡仪表盘气质（仅作配色/信息密度参考）。

## 冲煮指导：按方式算出每一段

冲煮指导是**可播放的分步方案**，不是一段死文字。选器具/手法后，用粉量和粉水比**算出每一段的用水**，并写清这一段怎么倒、要达成什么。

总水量 `= round(粉量 × 粉水比)`。各段按该方式的比例切分，**最后一段吃掉四舍五入的余数**，保证加总等于总水量。改粉量或比例，表格立刻重算。豆卡可存一套默认方式，播放时仍能临时换。

每一段固定这些字段：

- **本段用水**（这注倒多少克；滴滤为 0）
- **累计目标**（秤上要看到的克数）
- **本段时间**（建议秒数；播放时倒数，冲完可记下实际秒数）
- **累计时间**（从第一段加到这一段的建议总秒）
- **方式**（绕圈 / 中心注 / 停手等）
- **目标**（这一段要做成什么状态）
- **功能**（对萃取起什么作用：排气、提酸、补甜、加厚度、收尾）
- 动画场景键（`bloom` / `spiral` / `center_pour` / `drawdown` 等）

整套指导还要有**建议总时间**。记「冲一次」时可带上实际各段秒数和总时间，方便对照研磨。时间不是可有可无的装饰。

**布局**：冲煮内容多，豆卡上**单独占一整行**（表格 + 播放），不要和库存、雷达挤成四宫格或两列把表格挤窄。上面可以是库存（带图标）和雷达，下面整宽冲煮。

第一期内置方式（可改比例，不当成唯一真理）：

- **V60 四段**：闷蒸 `2 × 粉量` → 一注到总水 60%（螺旋）→ 二注到 100%（螺旋收回中心）→ 滴滤停手。闷蒸排气湿润；一注出酸与甜；二注补浓度和厚度；滴滤看总时间判研磨。
- **Hoffmann 一杯**：闷蒸 `2 × 粉量`，余下均分成 4 注，由中心向外。功能偏均匀、好复制。
- **4:6（粕谷）**：前 40% 拆成 2 注（调酸/甜），后 60% 拆成 3 注（调浓度）。两段的水量比可微调。
- **Kalita**：闷蒸 `2 × 粉量`，余下 3 注偏中心、少猛绕圈，功能是平底更均匀、少细粉通道。

播放时大字强调当前段：「本段 +xx g · 秤到 xx g · 本段 ss / 已过 ss」+ 方式/目标一行。动画跟场景键走（anime.js SVG，见[官方文档](https://animejs.com/documentation/svg)）。播完一键记消耗：粉量带出你这次算方案时输入的值作为**待确认的默认**，但记的必须是**当次实际用量**，人可以改成秤上真实的数再确认，并带上本次计时。

样张见 [_Doc/2026-09-04-ui-样张/index.html](../_Doc/2026-09-04-ui-样张/index.html)。

# ✅ 已完成：豆子补给计价评价、酒水、日历出表、简单部署

## 豆子：补给、曲线、谁喝、打分、价格、每杯成本

- **需要买豆子的补充**：每只豆设安全库存（克）。剩余低于阈值，或按近 14 天消耗速度估算「还能冲的天数」过短，进入**补货清单**（豆名、剩余、建议补袋重、上次购入价）。**每条补货都能上传图片**（货架、淘宝截图、上次包装、想买的那袋），方便对照去买；可缺。照片进 `data/photos/`，和豆卡一样不入库。基酒补货同样能传图。
- **消耗速度曲线**：按日/周汇总该豆（及全吧台）消耗克数，画一条曲线；风格跟全站 token 一致，不做另一套图表皮肤。
- **谁喝的**：消耗流水挂人。人是**可自由管理的实体**（增 / 改名 / 停用 / 删除），谁都能选，每笔都有追踪记录，选错了能撤回。见「谁喝的：自由管理 + 可撤回」。
- **评价维度打分**：豆卡上多次杯测记录。默认维度（1–10）：干香、风味、余韵、酸质、甜感、醇厚度、平衡、总体；可写评语。豆库页可按各维度排序。
- **豆子价格**：按**购入批次**记单价与袋重（例如 200 g / 128 元），不要只留一个模糊数字。袋重先记**包装标称**，开袋后可补**实称**（见下节）。
- **每杯多少钱**：每克单价 = `批次买入价 ÷ 可用克重`（可用克重 = 开袋实称有则用之，否则用包装标称）。**某一杯的实际钱 = 那笔的实际粉量 × 当时的每克单价**；豆卡上"这杯约 ¥x"是用**平均每杯粉量**做的估计（见下节），不是拿固定 15 g 算的。

### 平均每杯粉量：从实际用量算出来，不假设固定值

每次冲煮扣的是**当次实际用了多少克**（14 g、16 g、随手多一点都算数），不是每次都记 15 g。所以「还能冲几杯」这类估算不能拿一个假想值硬算，要用**你自己的平均每杯粉量**——这个数由系统从历史流水统计出来，不用人填。

- **口径**：`Σ 实际粉量 ÷ 杯数`，只算咖啡消耗、且**排除已撤回**的流水。
- **分层取值，就近优先**：

  1. **这支豆**最近 20 杯的平均（不同豆习惯本来就不同，浅烘可能用得多）
  2. 这支豆还没冲过 → **全吧台**最近 50 杯的平均
  3. 一杯都还没冲过 → 兜底 15 g，并注明「还没数据」

- **同时给区间**，例如「平均 15.6 g（14–17）」。只给一个平均值会掩盖波动，看不出自己是稳定还是随手。
- **全站统一走这个数**，不要各处各算一套：豆卡与豆库的「还能冲约 n 杯」、豆卡的「这杯约 ¥x」、见底提醒的阈值（低于一杯的量才提示）、统计页把它作为一个数字露出来（我平均一杯用多少粉）。
- 补货的「还能撑几天」按**克/天**的消耗速度算，与粉量无关，不受这个数影响。

### 成本要冻结：每笔消耗记下当时的单价

上面这个算式的分母（可用克重）**会变**：开袋补了实称、中途盘点校正、关袋结清偏差，都会改它。如果统计每次都拿"现在的分母"重算历史，那上周那笔消耗的成本就被回溯改写了——统计页「喝掉的钱」昨天 ¥742、今天 ¥756，数字一会儿一个样，人就不信它。

约定：**写每笔消耗流水时，把当时的每克单价快照存在这条流水上**（`ConsumptionEvent.unit_cost`，元/克）。

- 历史流水的钱**不可变**：统计、日历、画像、出表都读快照，不回头重算。
- 分母变了不追改旧流水：开袋实称、盘点校正、关袋偏差各自作为**新的一笔**调整入账，钱的变化落在发生的那一天，而不是把过去改掉。
- 豆卡上"这杯约 ¥x"是**按当前分母算的前瞻估计**，会随实称/校正变，这是对的；它和历史统计是两个数，界面上别混着写。
- 酒同理：同一张 `ConsumptionEvent`（`kind=drink`）记下当时的每毫升单价（批次买入价 ÷ 标称容量）。

## 包装克重 ≠ 实重，以及「这袋用不用完」

包装上印的克重和秤上的实重常有几克到十几克出入（含水、袋皮、装填公差、最后一点粉扫不干净）。**不能把标称克重当成一定能冲完的库存。**

批次同时记住三笔数，账面剩余只跟「可用克重 − 已消耗 − 校正」走：

| 字段 | 含义 |
| ---- | ---- |
| 包装标称克重 | 袋上印的，入库必填。**默认就用它当可用克重**，刚拆袋按它开始扣 |
| 开袋实称克重 | 可选，**通常不填**。想较真、手边正好有秤时才补一笔；有则它取代标称成为可用克重 |
| 账面剩余 | 可用克重减去消耗与校正；冲的时候扣这个 |

**实称不是必经步骤。** 刚拆一袋豆通常不会去称，只知道袋上印的数字——所以默认路径就是「按标称开始扣」，界面上不要把「开袋实称」做成拦路的必填项或强推的下一步。它只是给愿意较真的时候留的口子。

处理办法（都记流水，不偷偷改数字）：

1. **开袋实称（可选）**：默认按标称扣，什么都不用做。哪次手边有秤想校准，就补一笔实称，之后按实重扣。
2. **中途盘点**：袋里还剩一些时称一下，记「校正」到实重（可正可负）。
3. **这袋用完**：操作者明确点「这袋冲完了」。系统把该批次标为用完；若账面还剩几克，记一笔**偏差结清**（损耗/袋皮/扫不净）；若账面已是负数（标称不够喝），记一笔**短装/多耗**后归零。不自动把袋子关了。
4. **系统提醒，人确认**：账面剩余不够**平均一杯粉量**时提示「这袋是不是见底了？」——只提醒，点确认才关袋。账面到 0 但人说袋里还有，走盘点补重，不关袋。
5. **豆卡上能看见偏差**：标称、实称（若有）、累计消耗、账面剩余、关袋时的偏差克重。出表带上这些列，方便判断「这包到底有没有冲完、差了多少」。

补货清单以**未关袋批次的账面剩余**和消耗速度为准。同一只豆可以同时有几袋：一袋在喝、几袋未开封。**冲的时候扣哪一袋由人选**，不自动 FIFO，见「冲一次：袋子由人选」。

## 同豆多袋、照片可缺、用完仍留历史

- **豆卡是品种，袋子是批次。** 西达摩水洗只建一张卡。再买同样的豆点「再入一袋」，只加 `BeanLot`（价格、标称、购入日），产地/烘焙/风味/冲煮指导/杯测**不用重填**。只有配方或烘焙明显变了才新建卡或另记备注。
- **照片两种，都可以缺：** `pack` 包装袋、`tray` 豆盘里的豆子。没开封往往只有包装、没有豆盘；开封后再补豆盘。缺图用占位，不挡建卡。豆库缩略图优先豆盘，没有就用包装。手机直出多是 HEIC，浏览器认不了，一律转成 JPEG 存；长边压到 1600 并另存一张缩略图，原图不留（自用场景没必要占空间，也省得备份包变大）。
- **豆种（`varietal`）单独一个字段**：包装上一般印 Varietal（黄波旁 Bourbon Amarelo、伊鲁巴博森林 Illubabor Forest 等），和产地、处理法、烘焙度并列，不要塞进备注。
- **开封是一个显式动作，带动画。** 未开封的袋子在豆卡上有「开封」入口，点了播一段 anime.js SVG：拉链滑开 → 袋口向两侧翻开 → 豆子露出来 → 香气飘散，约 1.8 秒。**开封只记日子，不动克数**——撕开袋子并没有让豆子变少。播完顺势问一句要不要称（可选，留空就继续按标称扣）。第一次冲煮时若还没标开封，也会自动补上开封日，显式开封是为了那一下仪式感。
- **库存区用图标说话**：袋数、账面克、大约杯数（按平均粉量）、这杯钱，不要只有干巴巴三行字。**账面克是最主要的信息**——直观看还有多少量、还能冲几杯、要不要补，这是库存区存在的理由。
- **用完的豆子不删。** 所有批次关袋后，豆卡进「历史」：风味标签、历次杯测雷达、冲煮记录、照片、各袋偏差都在。豆库默认「在库」，可切「历史 / 全部」。出表能导出已结束的豆。画像统计也读历史，不因没货就抹掉口味。

## 豆库独立页：一眼看剩余 + 多规则排序

独立路由（例如 `/beans`），不是豆卡里的附带列表。打开就要**一眼看完所有在库豆子还剩多少**。点卡片再进豆卡详情。

每张豆卡一行/一格至少露出：缩略图、名字、烘焙、产地、账面剩余克、**克价**（元/克）、大约还能几杯（按**平均每杯粉量**换算，不按固定 15 g）、**剩余进度条**。进度条 = 未关袋批次账面剩余 ÷ 该批次可用克重（实称优先，否则标称）。见底（不够平均一杯）进度条用警示色，所有批次都关袋后进「历史」，默认不和在库混排；可切「历史 / 全部」。历史卡仍能点开看风味和冲煮记录。

桌面：网格或紧凑表，进度条横向拉满卡片底；手机：单列大卡，进度条同样一眼能读。风格走全站 token，进度用短动效填入，不要另做皮肤。

**排序 / 筛选**（可切换，当前规则要停在本机，刷新还在）：

| 规则 | 依据 |
| ---- | ---- |
| 浅烘 / 中烘 / 深烘 | 豆卡烘焙度；可当筛选芯片，也可按浅→深或深→浅排 |
| 酸味 | 最近一次杯测的「酸质」分；没打过分的排后面 |
| 甜味 | 最近一次杯测的「甜感」分 |
| 香味 | 最近一次杯测的「干香」分 |
| 剩余量 | 未关袋账面克重，多→少或少→多 |
| 克价 | 买入价 ÷ 可用克重（元/克）；一支豆多袋按还剩的克加权。没填价钱的垫底，不藏 |
| 评分 | 最近一次（或平均）总体分 |
| 地区 | 产地（国家/产区）字母或中文序；也可先按产区分组再排 |
| 水温 | 默认冲煮指导里的水温，高→低或低→高；没有指导的排后面 |
| 开封时间 | 当前在喝那袋的开封日（首次开袋实称、或第一次消耗、或手填开封日），新→旧或旧→新 |

同一时刻以一条主排序为准，允许再加烘焙度芯片和**自由标签**做筛选（例如只看浅烘 +「水洗」，再按剩余量排）。没有某字段的豆子不藏掉，统一垫底，避免「没填水温就从库里消失」。

批次要记 **开封日**；冲煮指导水温本来就会存，豆库排序直接读，不另做一套数。

## 自由标签：能打、能筛、交互简单

标签是自由词，不预先建分类树、不强制色板、不做独立「标签管理后台」。豆卡、酒瓶、配方上都能打；豆库（以及酒的列表）能按标签筛。

交互压到最少：

1. **打**：豆卡上一个输入框，回车或选补全即打上。打过的词下次自动出现，不用先去某处「新建标签」。
2. **摘**：点卡片上标签旁的叉，一下去掉。
3. **筛**：豆库顶上一行芯片（当前库里用过的标签）。点一下只看带这个标签的豆；再点取消。多选几个标签 = **同时都带**（越点越少）。一键「清除筛选」。
4. **看见**：豆库卡片上露出标签，不用点进详情才知道打了什么。

不要求先学规则：没有层级、没有必填、空着也能用。人名（谁喝的）也是同一套「输入即有」，只是打在消耗记录上，不和豆卡风味标签混在同一行筛选里，避免「埃塞」和「同事孙琦」搅在一起。没用过的词不必专门删除，不占界面即可。

## 用户画像：他喜欢喝什么样的

按「谁喝的」人名，从消耗流水自动汇总，**不另填问卷**。点一个人名就出一张画像，交互和标签一样简单。

画像至少包括：

- **一句话总结**（规则拼出来即可，例如「戚浩辰偏爱浅烘、高酸的埃塞水洗，酒只偶尔喝威士忌酸」）。
- **口味条**：把他喝过的豆子上最近杯测的酸质 / 甜感 / 干香做加权平均（喝得多的权重大）。
- **数字**：这个人累计/本月喝了多少克豆、多少毫升酒、酒精约多少克、对应花了多少钱、多少杯。不要只有「12 杯」这种笼统计数。
- **常喝**：豆、鸡尾酒、酒瓶，按杯数和克/毫升一起写。
- **偏好芯片**：出现最多的烘焙、产地、处理法、物品标签。
- **时间**：他常在哪几天喝（可点进日历滤这个人）。

咖啡和酒做在同一张画像上，分成两块，不拆两个系统。样本太少（例如不足 3 杯）就写「还不够判断」，不强行总结。出表可导出该人的汇总行。

看统计、看画像、导出都不占写锁。

## 酒：基酒、酒单、鸡尾酒、自制基酒、喝了什么

与豆子同一套 UI 和写锁，不另做独立站点。

- **基酒（买来的）**：一瓶金酒、一瓶波本这种。建档至少填 **酒名**、**买入价**，边上还要记 **风味类型**（如香草焦糖、柑橘杜松、泥煤；可当自由标签）和 **酒精度**（% vol）。列表每一行都要能看见这四项，不要点进去才知道几度。建议再记标称容量（ml）、品类、购入日、照片。同样的基酒再买一瓶只加批次，风味和酒精度沿用酒名，除非这瓶明显不同再改或备注。倒一杯按毫升扣；画像里的「酒精约多少克」用酒精度估算。
- **推荐酒单**：今日/常驻出品，一条指向鸡尾酒或某支基酒；可排序、上下架。
- **鸡尾酒配方**：材料引用基酒或辅料，写用量和步骤。
- **自制基酒配方**：浸泡 / 糖浆等「先做出来再调」的，和买来的基酒分开。成品可以当材料被鸡尾酒引用。
- **喝了哪些酒的统计**：按酒名、配方、品类汇总；可按人名过滤。

低库存基酒进补货清单。出表带酒名、买入价、风味类型、酒精度、剩余毫升。

## 统计：先出数字，再画图

统计页**一上来就要看见数字**，不能只有曲线或「谁喝了几杯」。默认看本月，可切本周 / 今年 / 全部。数字从消耗流水和批次价汇总，不另手填。

**所有统计一律排除已撤回（`voided_at` 非空）的流水**，统计页、日历、画像、出表口径一致；撤回的行只在明细里以划掉样式出现，不进任何汇总。

顶部至少这几块（大号数字 + 单位 + 一句来源）：

| 数字 | 怎么算 |
| ---- | ---- |
| **咖啡豆消耗** | 期间冲煮扣掉的账面克重合计；超过 1000 g 同时标 kg |
| **咖啡杯数** | 同期未撤回的咖啡消耗条数 |
| **平均每杯粉量** | 豆克数 ÷ 杯数，附区间（如 `15.6 g（14–17）`）。这是「我习惯用多少粉」，也是全站换算杯数的依据 |
| **酒消耗** | 期间倒掉的毫升合计（基酒 + 鸡尾酒里的酒） |
| **酒精约克数** | 各笔毫升 × 该酒酒精度 % vol × 0.789；鸡尾酒按配方拆到基酒再估 |
| **酒杯数** | 同期饮酒事件条数 |
| **喝掉的钱** | 各笔流水上**冻结的单价快照** × 该笔克重/毫升，直接求和。按「已经喝掉的」摊，不是库存原值；不拿今天的分母重算历史 |
| **买进来的钱** | 期间新建批次的买入价合计（豆袋 + 酒瓶），和「喝掉的钱」分开写，避免混 |

其下再放：

- 消耗速度曲线（豆克 / 日，酒毫升 / 日可叠或分图）
- **按人拆开**：每人同样给出豆克、酒毫升、酒精克、喝掉的钱、杯数；点人名进画像
- **按豆 / 按酒排行**：谁被喝得最多、对应多少钱
- 出表把这些汇总行和明细一起带走

没有流水就显示 0，不要空白卡片。看统计不占写锁。

## 日历与出表

- **日历**：月视图标出哪天冲了咖啡、哪天喝了酒（点进去看当日流水：什么豆/什么酒、谁喝、克或毫升、大约成本）。咖啡消耗与饮酒事件进**同一本日历**。
- **出表**：统计页和日历提供「导出 CSV」（UTF-8 BOM，Excel 能直接打开）。至少能出：豆库与剩余、补货清单、消耗明细、杯测分数、批次标称/实称/账面/关袋偏差、酒瓶与剩余、饮酒明细、按日汇总、**统计汇总（豆克 / 酒毫升 / 酒精克 / 喝掉的钱 / 买进来的钱 / 按人）**、标签列。不强制 xlsx，避免安装额外办公组件。

## MCP：让 Cursor 接管记账

网页手填和 **Cursor 代填** 是同一条路。你在对话里丢豆袋照片、产地、克重、价格，Cursor 调 MCP 写入小主机；打开豆库应立刻能看到。不另做一套「仅 Agent 用」的库。

形态：

- 仓库内一个本机 MCP（stdio，例如 `uv run coffeebar-mcp`）。
- Cursor 用本仓库或用户级 MCP 配置指向它；只连 `localhost`（或内网），带口令。
- 工具内部打现有 HTTP API（或同一套服务函数），**共用写锁**：网页正在改这张豆卡时，MCP 写入被**硬拒绝**并说明谁在编辑、多久前。Agent 不接管锁、不自动轮询重试（见「网页侧是软锁」）。
- 图片：工具收本机绝对路径或对话附件落盘路径，服务端拷进 `data/photos/` 并转码；**不把照片内容写进 Git**。

# ✅ 已完成：第一刀范围与三条落地决定

开工前把会影响建表的歧义定死，避免第一天返工。**第一刀只做豆子**：豆库、豆卡、批次、冲煮、消耗、补货、统计。第一期**不含酒、不含 MCP**——酒那边"鸡尾酒引用基酒、自制基酒本身又是含酒的配方"这层嵌套还没定，先不进第一刀。

事件表已合并（见「信息结构」）：`StockEvent` 管改数的动作，`ConsumptionEvent` 管喝掉一次，咖啡与酒同表不双记；统计、日历、画像只读 `ConsumptionEvent`。

## 冲一次：袋子由人选

**扣哪一袋是人当场选的，系统不替人决定。** 因为单价快照按批次取，选错袋子钱就错了，所以这个选择必须看得见、不能藏在后台。

- 「冲一次」对话框里列出这支豆**所有未关袋的批次**，每行看得见：购入日、标称 / 实称、账面剩余、单价、是否已开封。
- 默认选中**上次冲用的那袋**（没有上次就选最近开封的），但永远可改。
- **不做自动 FIFO**，不因为哪袋更早买就静默切换。莫名扣到未开封的袋子上是不能接受的。
- 未开封的袋子也能直接选，等于当场开第二袋，不强制先把上一袋关掉。
- 选中批次的账面剩余不够这次粉量时，提示并让人决定（换袋 / 改粉量 / 先盘点补重），不静默扣成负数。

## 谁喝的：自由管理 + 追踪 + 可撤回

人是**实体**（`Person`），不是写死在流水里的字符串。这样改名只改一行，历史记录自动跟着变。

- **自由管理**：随时新增、改名、停用、**删除**。输入框仍是「输入即创建」，打个新名字就有这个人，不用先去后台建档。
- **谁都可以选**：选人是从现有的人里挑，任何人都能被选到任何一笔上；也可以不选（留空）。
- **停用是轻量选项**：只是从选人列表里收起来，名字和归属都还在，随时能恢复。
- **删除是真删**：人这一行没了。**他名下的消耗流水不跟着删**，只是失去归属变成「没记」——那些豆是真扣过的、钱是真花过的，删个人不该让库存账和统计总数跟着变。删之前界面会说清有多少条会变成「没记」；想把记录留给别人，先「改归属」挪走再删。每条失去归属的流水都记一笔痕迹（原来是谁、什么时候删的），以后还能回答「这笔以前算谁的」。
- **追踪记录**：每个人一页，按时间列出他所有的消耗（哪天、什么豆、哪一袋、多少克、多少钱），画像页是这份记录的汇总视图。

### 撤回

选错了要能改回来，而且账要对得上：

| 情形 | 怎么处理 |
| ---- | ---- |
| **人选错了** | 直接改这条流水的 `Person`。克重没变，库存不动；记一笔改动痕迹（改前是谁、什么时候改的） |
| **整笔记错了** | 撤销这一笔：库存把克重加回去，这笔的钱退出统计 |
| **粉量记错了** | 撤销后重记一笔，不原地改数字 |

撤销的实现约定：

- **不物理删除**：流水标 `voided_at` + 撤销原因，出表能看到"这笔撤销了"，账目可追溯。
- 撤销后这笔的 `unit_cost` 快照一并失效，只影响它自己，不牵动别的行。
- **撤销已关袋批次上的消耗**：不去改那袋已经结清的偏差，把差额记成**今天的一笔 `StockEvent` 调整**。跟「钱不回溯」同一个原则——账目变化落在发生的那天，不改写过去。
- 撤销是写操作，占该资源写锁；不限时间窗（几天前记错了也能撤）。
- MCP 侧不自动撤销，需人明确指令，与「这袋用完」同等对待。

## 冲煮方案：按当场输入的豆重与粉重算

方案是**即时算出来的**，不是固化在豆卡上照着念的一段文字。

- 每次都按**当前输入框里的粉重**和粉水比算：总水 = `round(粉重 × 比例)`，各段按方式切分，最后一段吃余数。改粉重或比例，各段用水与累计秤重立刻重算。
- 同时带出**当前这袋的账面剩余（当前豆重）**，用来直观看还有多少量、还能冲大约几杯（按平均每杯粉量换算）、要不要补；不够这一杯就提示。
- **粉量记的是当次实际用量**，不是每次都写 15 g。输入框带出上次的值作为起点，但确认前应改成秤上真实的数。系统再从这些实际值反过来统计「我平均一杯用多少粉」，用于各处杯数估算。
- 豆卡上存的 `BrewGuide` 只是**默认值**（方式键 + 上次粉重 + 比例），作用是下次不用重填，不是锁定的方案。播放时也能临时改。
- 播放记下的实际各段秒数与总时间，存在**那条消耗流水**上（`brew_*`），不自动回写成新的默认；要变默认得人主动点「存为默认」。

## 附带定下的默认（不再单独问）

- **一天的分界用凌晨 4 点**：晚上 11 点开的酒喝到凌晨 1 点，算前一天。统计/日历/画像的"本日"都按这个走。
- 计量单位：豆按克（整数），酒按毫升（整数），钱按元（两位小数）。
